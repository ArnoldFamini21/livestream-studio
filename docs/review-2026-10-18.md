# Studio engineering review — October 18, 2026

Baseline: `e421a5c76ebff0fcca643dffabca631aacf4803d` on `main`.

This review inspected the current client, signaling/API service, media service,
recording/upload/export paths, permissions, tests, and deployment workflows.
Three independent review tracks covered security, recording integrity, and
client media lifecycle. Findings were cross-reviewed before implementation.

The product has substantial breadth. The route to StreamYard/Riverside parity
now depends on protecting footage, enforcing permissions across every media
path, surviving interruptions, and qualifying the system under sustained load.
More controls alone will not establish parity.

## Recording durability and lifecycle repairs in the second batch

- **P1 — Saved library files could become unreadable after reload.** Real
  Chrome reproduced a playable saved recording becoming a black 0:00 preview
  with `ERR_FILE_NOT_FOUND` after navigation. IndexedDB's Blob still referenced
  OPFS capture fragments, while acknowledgement/recovery cleanup deleted those
  fragments. Retain explicit library ownership, check authoritative library
  references before cleanup, and protect readers with document-scoped locks.
  This avoids loading multi-gigabyte recordings into memory to detach them.
- **P1 — A supported container did not provide recoverable fragments.** In
  real Chrome 155, the preferred H.264 MP4 video recorder committed no media
  fragments during a four-second take despite a one-second timeslice. The
  same canvas recorded as WebM committed multiple fragments before Stop, and
  its interrupted take could be recovered and played. Prefer WebM video when
  supported, retaining MP4 for browsers without it and final export. Encoding
  readiness probes use the same selection. Audio MP4 did emit progressive
  chunks in the comparison and keeps its existing preference.

- **P1 — Stop can lose a race with authorization.** `StudioRoom.onGoLive` and
  `useRtmpRelay` await readiness, authorization, mixer creation, and reconnect
  work without complete attempt ownership. Stop during an await can be followed
  by a late socket/start; an old handshake timeout can tear down a newer relay.
  Scope cancellation across the UI attempt, hook session, socket, and mixer.
- **P2 — Old SFU async work can reach a replacement.** Socket ownership alone
  does not isolate an old publish offer, subscribe offer/answer, timeout, or
  transport close. Reset participant negotiation state, scope async results to
  a lifecycle, and detach captured peer connections before awaiting shutdown.

## Material findings still requiring a separate design/implementation

### P1 — SFU membership is not revoked with signaling membership

`server/src/services/signaling.ts` removes/bans participants on the signaling
service, while `media-server/src/index.ts` authenticates SFU membership once.
An existing media socket can continue consuming after its signaling participant
is removed. `sfuAuth.ts` also accepts legacy recording-upload credentials for
SFU access, and token issuance permits backstage guests even though the client
intends SFU for on-stage media only.

The repair needs an authenticated, authoritative membership/status control
plane between services, immediate transport revocation, expiry enforcement,
and tests for ban, removal, green-room/backstage transitions, and reconnects.
Shorter token lifetimes alone do not provide immediate privacy enforcement.

### P1 — Anonymous requests can consume paid AI and renderer capacity

When configured with an OpenAI key, the transcription, highlights,
episode-content, and translation routes invoke the provider without account
authorization or service entitlement.
The media service's presentation preview/PDF endpoints accept large anonymous
uploads and launch rendering processes without a bounded concurrency queue.
The renderers share the host running live media processing.

Require authenticated authorization before reading large bodies; use
operator-controlled AI entitlements and bounded per-account/global budgets.
A freely created anonymous room token alone is not a spending barrier. Give
rendering a bounded worker queue and isolate it from live encoding. This review
did not make paid production AI calls or run a resource-exhaustion attack.

### P1 — Cloud recording metadata is not durable

`RecordingUploadStore.sessions` and `RecordingExportJobStore.jobs` are memory
maps. A process restart makes existing upload/export paths inaccessible even
when files remain on disk or private object storage. Expired sessions are
rejected before download/delete authorization; no general upload expiry sweep
reclaims the associated directories.

Persist upload manifests, committed offsets, job/artifact metadata, and recovery
state. Separate upload-token expiry from recording retention. Provide durable,
authorized artifact lookup and deletion plus observable lifecycle cleanup.

### P2 — Recording sidecars add avoidable memory and timing pressure

`useLocalRecording.ts` starts recorders sequentially around optional WebCodecs
sidecar initialization. This can delay later tracks while capture metadata
uses a common start time. `webCodecsRecording.ts` retains large per-track raw
buffers, copies them on finalization, and does not bound the encoder queue.

Start required capture tracks together, measure actual track origins, and keep
optional sidecars off the capture critical path. Gate sidecars behind an
explicit use case and enforce memory/encode-queue budgets. Verify alignment
with real media rather than timestamps alone.

### Architecture and qualification gaps

- The host browser still composites/encodes the program. Closing or suspending
  that device remains a show-level failure mode. Adopt a proven SFU plus
  server-side production/egress before claiming host-independent broadcasts.
- Signaling/live state remains process-local; optional persistence does not
  establish multi-replica failover. Use versioned migrations and qualify
  database/object-storage/TURN failure handling.
- `StudioRoom.tsx` is roughly 8,900 lines. Extract lifecycle owners incrementally
  as behavior is covered; a broad rewrite would risk existing production tools.
- The checked-in synthetic browser fixtures are useful, but CI does not yet
  run the real browser qualification matrix. Unit tests do not establish
  90-minute multitrack integrity, restrictive-network connectivity, broadcast
  failover, Safari/mobile behavior, or 10-person capacity.

## Acceptance criteria for the next milestones

1. **Privacy and admission:** removed/banned/backstage participants cannot
   retain unauthorized media through either mesh or SFU; enforce at the server.
2. **Recording durability:** interrupt network, process, and browser separately;
   recover acknowledged footage with no duplicated segments or false complete
   state; show missing tracks and preserve unacknowledged local media.
3. **Reliable live operation:** stop always wins over delayed starts/retries;
   one destination failure does not stop others; qualify real TURN and output
   failover under sustained congestion.
4. **Cloud production:** host browser closure does not end the program; establish
   measured CPU/network/capacity budgets and observable failover.
5. **Post-production:** export synchronized playable isolated tracks and a
   composite after restart; validate the transcript/cleanup workflow on real
   recordings before adding more editor surface.

These are engineering acceptance criteria informed by
[StreamYard's local-recording workflow](https://support.streamyard.com/hc/en-us/articles/10725401176596-Local-Recording-of-your-Live-Stream)
and [Riverside's recording checklist](https://support.riverside.com/hc/en-us/articles/5706937784861-Host-checklist-and-tips-Recording-on-computer).
They are not claims that the current implementation meets those products'
service guarantees.
